# راهنمای آزمون‌های فراتک (دور ۸)

این سند می‌گوید چه چیزی، با چه روشی و در کدام لایه آزمون می‌شود، چطور اجرا می‌شود و وقتی آزمونی شکست خورد کجا را نگاه کنیم.
هدف این است که برای اطمینان از درست کار کردن فروشگاه دیگر لازم نباشد برنامه را دستی اجرا و کلیک کنیم.

## ۱. لایه‌ها (از پایین به بالا)

| لایه | پوشه | دسته (Trait `Category`) | چه چیزی را می‌سنجد | پیش‌نیاز |
|---|---|---|---|---|
| واحد (Unit) | `tests/Fratak-Shop.Tests/Unit` | `Unit` (پیش‌فرض) | منطق خالص: قیمت، قواعد سفارش، اعتبارسنج‌ها، سئو، فایروال، رمزنگاری Web Push، کپچای پست و … | هیچ |
| معماری | `Unit/Architecture` | `Unit` · `Area=Architecture` | قانون‌هایی که با بازتاب روی کد کامپایل‌شده بررسی می‌شوند (جدول بخش ۳) | هیچ |
| مبتنی بر ویژگی | `Unit/Properties` | `Unit` · `Area=Properties` | FsCheck برای هر قاعده صدها ورودی تصادفی می‌سازد (نامک، متن جست‌وجو، فاصلهٔ ویرایشی، عدد به حروف، کارت/شبا، کارت هدیه، قیمت، بازهٔ IP) | هیچ |
| یکپارچه (Integration) | `Integration` | `Integration` | سرویس‌ها روی SQL Server واقعی (هر کلاس پایگاه دادهٔ خودش را می‌سازد و پاک می‌کند) | `FRATAK_TEST_SQL` |
| سرتاسری (E2E) | `E2E/<بخش>` | `E2E` (+ `Security` برای حمله‌ها) | کل برنامه با همان `Program.cs` و میان‌افزارهای Production، از راه HTTP مثل یک مرورگر | `FRATAK_TEST_SQL` |

### زیرساخت E2E (`E2E/Infrastructure`)

- `ShopApp`: برنامهٔ واقعی را در محیط **Production** روی `https://fratak.test` بالا می‌آورد (HSTS، ریدایرکت HTTPS، صفحهٔ خطا،
  فایروال، محدودیت نرخ، کش خروجی همه فعال‌اند). پایگاه دادهٔ جدا با مهاجرت‌ها و دادهٔ نمونه.
  - پیامک‌ها ضبط می‌شوند (`app.Sms`) تا کد OTP خوانده شود؛ هیچ پیامکی واقعاً ارسال نمی‌شود.
  - زرین‌پال با `FakeZarinPal` شبیه‌سازی می‌شود (همان JSON نسخهٔ ۴؛ حالت‌های قطعی، خطای تأیید، تأیید تکراری ۱۰۱).
  - هر کلاینت IP خودش را دارد (سرآیند `X-Test-Client-IP`) تا محدودیت نرخ و کپچای یک آزمون به آزمون دیگر نرسد.
  - هشدارها و خطاهای سرور ضبط می‌شوند (`app.Logs.ErrorsSince`)؛ هر پاسخ **۵۰۰** با متن کامل استثنای سرور شکست می‌خورد.
- `ShopClient`: کلاینت مرورگرمانند (کوکی، بدون دنبال کردن خودکار ریدایرکت، گرفتن توکن ضدجعل، ورود، تجزیهٔ HTML با AngleSharp).
- `TestData`: ساخت مشتری، محصول، شارژ کیف پول، افزودن به سبد و پر کردن فرم تسویه.

> نکته: هرگز رمز اشتباه برای حساب‌های نمونهٔ مشترک (۰۹۱۲۰۰۰۰۰۰۰ و کارکنان) نفرستید؛ ۵ خطا حساب را ۱۵ دقیقه قفل می‌کند.
> آزمون‌های حمله همیشه با مشتری تازه (`app.CreateCustomerAsync`) کار می‌کنند.

## ۲. بخش‌های سرتاسری (هر بخش مستقل، از ساده تا حمله)

| بخش | فایل | بهترین حالت | بدترین حالت و حمله |
|---|---|---|---|
| ویترین | `E2E/Storefront` | همهٔ صفحه‌های عمومی، نقشهٔ سایت، robots، مانیفست PWA با آیکون‌های نسخه‌دار | صفحهٔ ناموجود ۴۰۴، پیوندهای شکسته، نشت خطا |
| ورود و ثبت‌نام | `E2E/Auth/AuthFlow…` | رمز، کد پیامکی، ثبت‌نام، فراموشی رمز، خروج | حدس رمز (کپچا و قفل)، شمارش کاربران، OTP تکراری/منقضی |
| توکن‌ها | `E2E/Auth/JwtAttack…` | توکن دسترسی + تازه‌سازی، `/api/auth/me` | الگوریتم none، امضای جعلی، توکن منقضی، استفادهٔ دوباره از refresh (ابطال کل خانواده)، ابطال پس از تغییر رمز |
| خرید | `E2E/Shopping` | سبد → تسویه → پرداخت در محل/کیف پول/زرین‌پال → فاکتور → لغو | قیمت جعلی در فرم، آدرس دیگران، روش پرداخت تعریف‌نشده، موجودی تمام‌شده، درگاه قطع، callback جعلی/تکراری، کوپن منقضی |
| پروفایل | `E2E/Profile` | صفحه‌های پروفایل، آدرس، نشست‌ها | IDOR روی سفارش/فاکتور/آدرس/نشست دیگران |
| پنل مدیریت | `E2E/Admin` | هر نقش بخش‌های خودش را می‌بیند؛ خزش کامل پنل بدون ۵xx | مهمان → ورود، مشتری → ۴۰۴، نقش بی‌مجوز → «دسترسی ندارید» + ثبت رویداد امنیتی، CSRF، مسدودسازی مشتری |
| لایهٔ HTTP | `E2E/Security` | سرآیندهای امنیتی، HTTPS/HSTS، کوکی ضدجعل امن، سازگاری صفحه‌ها با CSP | تزریق SQL، XSS بازتابی، فایل‌های حساس و پیمایش مسیر، ریدایرکت باز، درخواست ناقص، فایروال IP و ابزار حمله، سیل فرم تماس (۴۲۹)، بمباران پیامکی، حالت تعمیرات |
| هم‌زمانی | `E2E/Concurrency` | — | ۸ callback هم‌زمان (فقط یک تأیید و یک شارژ)، رقابت روی آخرین کالا، برداشت هم‌زمان از کیف پول، افزودن هم‌زمان به سبد |

## ۳. قانون‌های معماری (`ArchitectureRulesTests`)

| قانون | چرا |
|---|---|
| هر صفحهٔ پنل `[AdminPermission]` یا `[AdminOwnerOnly]` دارد، مگر صفحه‌های فهرست استثنا (هر کدام با دلیل) | صفحهٔ جدید بی‌مجوز برای همهٔ کارکنان باز نمی‌ماند |
| صفحه‌های کارکنان فقط با `staff.manage` و صفحه‌های مالی با مجوز مالی | جلوگیری از افزایش دسترسی |
| هیچ هندلر GET نامی مثل Delete/Save/Pay ندارد | GET توکن CSRF ندارد |
| `IgnoreAntiforgeryToken` فقط روی صفحهٔ ۴۰۴ | همهٔ فرم‌ها در برابر CSRF محافظت می‌شوند |
| فرم‌های فروشگاه فیلدهایی مثل Role، WalletBalance، IsBlocked، PaymentStatus را bind نمی‌کنند | Over-posting |
| هر ستون decimal دقت صریح دارد | مبلغ‌ها گرد یا بریده نمی‌شوند |
| هر موجودیت دارای IsDeleted فیلتر حذف نرم دارد | رکورد حذف‌شده جایی نشان داده نمی‌شود |

## ۴. اجرا

```bash
# فقط واحد + معماری + ویژگی (بدون پایگاه داده؛ همان چیزی که گردش‌کار Build اجرا می‌کند)
dotnet test --filter "Category!=Integration&Category!=E2E"

# همه (نیاز به SQL Server)
export FRATAK_TEST_SQL="Server=localhost,1433;User Id=sa;Password=...;TrustServerCertificate=True;MultipleActiveResultSets=true"
dotnet test

# یک بخش
dotnet test --filter "Area=Checkout"          # یا Auth، Admin، Http، Concurrency، Architecture، Properties
dotnet test --filter "Category=Security"      # فقط شبیه‌سازی حمله‌ها
```

## ۵. CI

- **Build**: کامپایل کل راه‌حل و آزمون‌های واحد/معماری/ویژگی.
- **Verify**: SQL Server واقعی در سرویس Docker، همهٔ آزمون‌ها (Integration و E2E هم)، جدول «آزمون‌ها به تفکیک بخش»،
  درصد پوشش کد (coverlet، بدون Migrations)، گزارش بسته‌های NuGet آسیب‌پذیر و آپلود نتایج به‌صورت Artifact.
  آزمون‌های شکست‌خورده با پیام و stack trace به‌صورت کامنت روی همان commit نوشته می‌شوند.

## ۶. یافته‌ها و اصلاح‌های دور ۸

| یافته | اصلاح |
|---|---|
| اپ نصب‌شدهٔ PWA آیکون قدیمی را نشان می‌داد | آیکون‌های نسخه‌دار در مانیفست، سرویس‌ورکر v4، هدایت آدرس‌های آیکون قدیمی به فایل جدید |
| کش «مهر امنیتی» پس از تغییر رمز/مسدودی پاک نمی‌شد (توکن قدیمی تا ۲ دقیقه معتبر می‌ماند) | پاک‌سازی کش در UserService |
| زمان پاسخ ورود برای شمارهٔ ناموجود کوتاه‌تر بود (شمارش کاربران) | هش مساوی‌ساز زمانی |
| روش پرداخت تعریف‌نشده و تعداد بسیار بزرگ در سفارش | بررسی `Enum.IsDefined` و محدودسازی تعداد |
| صفحهٔ ۴۰۴ در صورت استثنا ۵۰۰ می‌داد | مدیریت خطا در Error404 |
| در حالت تعمیرات کارکنان نمی‌توانستند وارد شوند (توکن ضدجعل و کپچا مسدود بود) | استثنا کردن `/api/antiforgery` و `/api/captcha` |
| در تسویه، شناسهٔ آدرسی که مال کاربر نبود بی‌صدا با آدرس پیش‌فرض عوض می‌شد و سفارش به آدرسی می‌رفت که انتخاب نشده بود | خطای «آدرس انتخاب‌شده معتبر نیست» |
| روش پرداخت تعریف‌نشده (۹۹، Free، ‎-1) در فرم به روش پیش‌فرض «درگاه» تبدیل می‌شد | خطای «روش پرداخت انتخاب‌شده معتبر نیست» |
| قیمت تخفیفی منفی می‌توانست مبلغ سفارش را منفی کند | تخفیف منفی هرگز اعمال نمی‌شود |
| عدد به حروف برای مبالغ بسیار بزرگ استثنا می‌داد یا رقم جا می‌انداخت | محاسبه با decimal و مقیاس‌ها تا اکتیلیون |
| نرمال‌سازی جست‌وجو پس از برش ممکن بود با فاصله تمام شود | TrimEnd پس از برش |

موارد کم‌خطر پذیرفته‌شده: شمارش بازدید محصول توکن ضدجعل ندارد؛ عکس‌های مرجوعی با نام تصادفی عمومی‌اند؛ پیام قفل حساب وجود حساب را
نشان می‌دهد؛ توکن دسترسی پس از خروج تا انقضای کوتاهش معتبر است (refresh token فوراً باطل می‌شود).
