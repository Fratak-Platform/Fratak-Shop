# کارایی و پایداری روی هاست ضعیف (دور نوزدهم – فاز A)

هدف: سایت روی یک هاست اشتراکی ارزان (Plesk/IIS)، حتی وقتی چند پروژهٔ دیگر روی همان سرور هستند یا هزار نفر هم‌زمان می‌آیند،
**از دسترس خارج نشود** (خطای ۵۰۳ نبیند). این سند می‌گوید برنامه خودش چه می‌کند و مدیر هاست چه چیزهایی را باید تنظیم کند.

## ۱. برنامه خودش چه می‌کند؟

| بخش | کار | فایل |
|---|---|---|
| پروفایل منابع | سه پروفایل Low / Normal / High؛ همهٔ بودجه‌ها (کش، صف، استخر اتصال، …) از همین می‌آید | `Infrastructure/Ops/ResourceGovernor.cs` |
| نمونه‌بردار منابع | هر ۵ ثانیه حافظه/CPU/صف؛ زیر فشار کش را سبک می‌کند، در خط قرمز GC کامل، و در صورت لزوم ری‌استارت کنترل‌شده در ساعت خلوت | `Ops/ResourceMonitorService.cs` |
| نوبت کارهای پس‌زمینه | فقط یک کار سنگین هم‌زمان؛ هیچ کار سنگینی در دقایق اول بعد از روشن شدن؛ زیر فشار بالا صبر؛ کارهای غیرفوری (سئو، گزارش‌ها) در ساعت شلوغ فقط با فشار «عادی» | `Admin/JobMonitor.cs` + `ResourceGovernor.EnterAsync` |
| صف ورودی | حداکثر N صفحهٔ مهمان هم‌زمان ساخته می‌شود؛ بقیه چند ثانیه صبر می‌کنند؛ اگر صف پر شد «آخرین نسخهٔ سالم» صفحه (۲۰۰) | `Ops/LoadShedding.cs` |
| آخرین نسخهٔ سالم | HTML صفحه‌های عمومی مهمان هر ۱۰ دقیقه روی دیسک (`App_Data/page-snapshots`)؛ هنگام خطای پایگاه داده، شلوغی یا در حال روشن شدن نشان داده می‌شود | `Ops/PageSnapshots.cs` |
| ربات‌های پرمصرف | Ahrefs/Semrush/MJ12/… در robots.txt «Crawl-delay: 10» و در عمل هر ۳ ثانیه یک درخواست (بیشتر = ۴۲۹)؛ زیر فشار هیچ. گوگل و بینگ هرگز محدود نمی‌شوند | `LoadShedding.cs` (`HeavyCrawlers`) |
| قطع‌کن مدار | بعد از ۵ شکست پشت‌سرهم یک سرویس بیرونی، تا ۱ دقیقه (حداکثر ۱۰) درخواستی فرستاده نمی‌شود؛ مهلت پیش‌فرض ۳۰ ثانیه. پیامک و پرداخت هرگز | `Infrastructure/Http/CircuitBreaker.cs` |
| پایگاه داده | استخر DbContext، سقف Max Pool Size، مهلت فرمان ۳۰ ثانیه، شمارش پرس‌وجوی هر صفحه | `Data/Extensions/FratakShopBootstrapper.cs`، `Ops/QueryMetrics.cs` |
| شروع سبک | فهرست شهرها و راهنمای پنل فقط وقتی نسخه یا پایگاه داده عوض شده باشد (`App_Data/startup-sync.txt`)؛ گرم کردن کش‌ها بلافاصله بعد از آماده شدن | `FratakShopBootstrapper.cs`، `Ops/WarmupService.cs` |
| فایل‌های ایستا | CSS/JS با Brotli/Gzip فقط یک بار فشرده و در حافظه نگه داشته می‌شوند (سقف ۱۶ مگ)؛ با `?v=` کش یک‌ساله | `Ops/PrecompressedStatic.cs` |
| تصویر | تبدیل WebP یکی‌یکی (صف)، باز کردن کوچک‌شدهٔ عکس‌های خیلی بزرگ؛ در پنل، عکس پیش از آپلود در خود مرورگر WebP و کوچک می‌شود | `Media/WebPEncoder.cs`، `wwwroot/assets/js/upload-webp.js` |
| حافظهٔ GC و کد | Workstation GC غیرهم‌زمان + `ConserveMemory=5`؛ کامپایل یک‌مرحله‌ای (`TieredCompilation=false`، بدون PGO)؛ سقف هیپ = ۶۰٪ سقف برنامه؛ یک پاک‌سازی کامل یک دقیقه بعد از شروع | `Fratak-Shop.Web.csproj`، `MemoryLimits` در `ResourceGovernor.cs` |
| اتصال زنده | روی پروفایل Low فقط کارکنان اتصال SignalR دارند (هر اتصال یک درخواست باز است) | `Pages/Shared/_Layout.cshtml` |
| گزارش | پنل ← فنی ← **منابع سرور**: فشار، حافظه، صف، کارهای منتظر، قطع‌کن‌ها، سنگین‌ترین صفحه‌ها، تاریخچهٔ روشن/خاموش شدن با دلیل | `Areas/Admin/Pages/System/Resources.cshtml` |

### بودجهٔ پروفایل‌ها

| پروفایل | سقف فرضی حافظه | کش صفحه | درخواست هم‌زمان | صف | انتظار صف | کار سنگین هم‌زمان | دورهٔ آرام شروع | استخر DbContext | Max Pool Size | اتصال زندهٔ مشتری |
|---|---|---|---|---|---|---|---|---|---|---|
| **Low** (پیش‌فرض) | ۱۰۲۴ مگ | ۴۸ مگ | ۸ | ۴۸ | ۴ ثانیه | ۱ | ۱۰ دقیقه | ۳۲ | ۴۰ | خاموش |
| Normal | ۲۰۴۸ مگ | ۱۲۸ مگ | ۹۶ | ۱۹۲ | ۵ ثانیه | ۱ | ۵ دقیقه | ۶۴ | ۱۰۰ | روشن |
| High | بدون سقف | ۲۵۶ مگ | ۲۵۶ | ۵۱۲ | ۵ ثانیه | ۲ | ۲ دقیقه | ۱۲۸ | ۲۰۰ | روشن |

اگر سقف واقعی حافظهٔ استخر IIS کمتر باشد، برنامه خودش همان را می‌خواند (حافظهٔ در دسترس GC) و کمینه را به کار می‌برد.

## ۲. تنظیمات (appsettings.json یا متغیر محیطی)

```json
"Shop": {
  "Resources": {
    "Profile": "Low",
    "MemoryLimitMb": 0,
    "MaxConcurrentRequests": 0,
    "StartupQuietMinutes": -1,
    "SelfRestart": true,
    "QuietHourStart": 3,
    "QuietHourEnd": 6,
    "BusyHourStart": 9,
    "BusyHourEnd": 24,
    "PageSnapshots": true,
    "DbContextPooling": true
  }
}
```

| متغیر محیطی (Plesk ← ASP.NET Settings) | معنی |
|---|---|
| `Shop__Resources__Profile` | `Low` / `Normal` / `High` |
| `Shop__Resources__MemoryLimitMb` | سقف حافظهٔ استخر به مگابایت (اگر هاست گفته، مثلاً `900`)؛ ۰ = خودکار |
| `Shop__Resources__MaxConcurrentRequests` | سقف دستی درخواست هم‌زمان مهمان؛ ۰ = از پروفایل |
| `Shop__Resources__StartupQuietMinutes` | دورهٔ آرام بعد از روشن شدن؛ ۱- = از پروفایل |
| `Shop__Resources__LimitGcHeap` | سقف هیپ GC = ۶۰٪ سقف حافظهٔ برنامه (پیش‌فرض `true`)؛ جا برای حافظهٔ غیرمدیریت‌شده می‌ماند و پروسه به سقف نمی‌خورد |
| `Shop__Resources__HeapPercent` | سهم هیپ GC به درصد (۳۰ تا ۷۵؛ ۰ = پیش‌فرض ۶۰). کمتر = جای بیشتر برای حافظهٔ غیرمدیریت‌شده، ولی زیر ۵۵ روی ۵۱۲ مگ هیپ خفه می‌شود |
| `MALLOC_ARENA_MAX` | فقط لینوکس: `2` حافظهٔ غیرمدیریت‌شده را کم می‌کند (در systemd، `docs/DEPLOYMENT.md`) |
| `Shop__Resources__SelfRestart` | ری‌استارت کنترل‌شده در خط قرمز حافظه (`true`/`false`) |
| `Shop__Diagnostics__QueryHeader` | فقط عیب‌یابی: سرآیند `X-Db-Queries` (روی سایت واقعی خاموش بماند) |

مقادیر نامعقول خودکار محدود می‌شوند (مثلاً سقف حافظه حداقل ۱۲۸ مگ، دورهٔ آرام حداکثر ۱۲۰ دقیقه).

## ۳. راهنمای Plesk / IIS (یک بار، توسط مدیر هاست یا خودتان)

1. **Application Pool ← Idle Time-out**: روی `0` (یا حداقل ۶۰ دقیقه). پیش‌فرض ۲۰ دقیقه یعنی بعد از هر ۲۰ دقیقه بی‌بازدید برنامه خاموش
   می‌شود و اولین بازدیدکنندهٔ بعدی چند ثانیه صبر می‌کند.
2. **Start Mode**: `AlwaysRunning` و در سایت **Preload Enabled** = True (اگر هاست اجازه بدهد).
3. **Regular Time Interval (بازیافت دوره‌ای)**: `0` و به‌جایش یک **زمان مشخص** شبانه (مثلاً ۴:۳۰ بامداد). بازیافت هر ۲۹ ساعت
   (پیش‌فرض IIS) ممکن است وسط روز بیفتد.
4. **Private Memory Limit**: اگر هاست سقف گذاشته، همان عدد را در `Shop__Resources__MemoryLimitMb` بنویسید تا برنامه پیش از رسیدن
   به سقف کش را سبک کند و در صورت لزوم در ساعت خلوت خودش آبرومندانه ری‌استارت شود (به‌جای کشته شدن ناگهانی و ۵۰۳).
5. **Rapid-Fail Protection**: اگر در دسترس است، `Maximum Failures` را به ۱۰ و بازه را ۵ دقیقه کنید (پیش‌فرض ۵ خطا در ۵ دقیقه
   استخر را متوقف می‌کند و تا روشن کردن دستی ۵۰۳ می‌دهد).
6. **.NET CLR / Pipeline**: `No Managed Code` و `Integrated` (برای ASP.NET Core همین درست است).
7. **پروفایل منابع**: هاست اشتراکی ارزان = `Low` (پیش‌فرض)؛ VPS دو گیگ = `Normal`؛ سرور اختصاصی = `High`.
8. **GC سرور را روشن نکنید** (`DOTNET_gcServer=1` فقط برای سرور اختصاصی چندهسته‌ای با حافظهٔ زیاد؛ روی هاست اشتراکی چند برابر حافظه
   می‌گیرد).
9. **ModSecurity**: اگر صفحه‌ای از پنل ۴۰۳ داد، شناسهٔ قانون را از Logs در Plesk پیدا و فقط همان را برای این دامنه غیرفعال کنید
   (docs/DEPLOYMENT.md).

بعد از انتشار، پنل ← فنی ← **منابع سرور** را باز کنید: پروفایل، سقف حافظهٔ مؤثر، مدت آماده شدن و رویدادها آنجا دیده می‌شوند.

## ۴. آزمون‌ها

- **واحد** (`tests/.../Unit/Performance/ResourceGovernorTests.cs`): بودجه‌ها، قانون فشار، نوبت کارها، دورهٔ آرام، ساعت شلوغ،
  ری‌استارت کنترل‌شده، ربات‌ها، قطع‌کن مدار (شکست، مهلت، لغو خودمان)، نسخهٔ ذخیره‌شده (خطای پایگاه داده)، صف ورودی و سیل بازدید
  (۲۰۰ درخواست هم‌زمان با ظرفیت ۴ ← همه ۲۰۰)، شمارش پرس‌وجو، فشرده‌سازی.
- **سرتاسری** (`E2E/Storefront/PerformanceE2ETests.cs`): بودجهٔ پرس‌وجوی صفحه‌های اصلی، robots.txt، ۴۲۹ ربات پرمصرف، فایل‌های
  پیش‌فشرده، صفحهٔ «منابع سرور» و دسترسی آن.
- **آزمون بار** (GitHub Actions ← Verify ← «Load test»، `tools/load/`): برنامهٔ منتشرشده در کانتینر با **۵۱۲ مگ حافظه و نیم هستهٔ CPU**،
  **۱۰۰۰ کاربر هم‌زمان** k6. شرط قبولی: صفر پاسخ ۵xx، صفر خطای اتصال، کانتینر زنده. اجرای محلی (لینوکس + Docker):

  ```bash
  dotnet publish src/Fratak-Shop.Web/Fratak-Shop.Web.csproj -c Release -o out -p:FratakPublishTarget=linux
  bash tools/load/run-load-test.sh out "Server=localhost,1433;Database=FratakShopLoad;User Id=sa;Password=...;TrustServerCertificate=True"
  ```

  برای آزمایش تنظیم دیگر: `LOAD_ENV="Shop__Resources__HeapPercent=65 DOTNET_GCgen0size=1000000" bash tools/load/run-load-test.sh …`.
  خروجی در GitHub به‌صورت annotation: «memory» (قلهٔ حافظهٔ غیرقابل‌بازپس‌گیری و حافظه بعد از گرم شدن)، «k6 summary»، «pressure»
  و در صورت خطای حافظه «oom stack».

  **یافته‌های آزمون بار (دور ۱۹)** — هر تنظیم دو بار روی ماشین جدا:

  | تنظیم | نتیجه |
  |---|---|
  | پایه (کامپایل چندمرحله‌ای، هیپ ۵۵٪) | پروسه کشته شد (OOMKilled) |
  | W^X خاموش، صف ۴، `GCgen0size` | بی‌اثر (فقط shmem به anon تبدیل شد) — کنار گذاشته شد |
  | هیپ ۴۵ یا ۵۰٪ | هیپ خفه شد: OutOfMemoryException و از کار افتادن پروسه |
  | `TieredCompilation=false` | دیگر کشته نشد؛ چند ۵۰۰ نادر از OutOfMemoryException هیپ |
  | + `MALLOC_ARENA_MAX=2` | قلهٔ حافظه ۴۰ تا ۶۰ مگ کمتر (۴۱۱ تا ۴۳۵ مگ) |
  | + هیپ **۶۰٪** یا ۶۵٪ | **۴ اجرا از ۴ بدون هیچ خطا**؛ قلهٔ کل ۴۴۳ تا ۴۶۲ مگ از ۵۱۲ ← پیش‌فرض فعلی |

  همچنین پشتهٔ OutOfMemoryException نشان داد نسخهٔ ذخیره‌شده برای مرورگر بدون gzip با بافر ۸۰ کیلوبایتی باز می‌شد (هیپ اشیای بزرگ)؛
  حالا بافر ۱۶ کیلوبایت است (`PageSnapshotStore.DecompressBufferBytes`).

## ۵. محتوای هوشمند روی هاست ضعیف (دور ۱۹)

* `SmartWorker` کار سنگین است: فقط با اجازهٔ مدیر منابع (`ResourceGovernor`، وزن Heavy) اجرا می‌شود؛ در فشار بالا صبر می‌کند و هر بار
  فقط یک کار برمی‌دارد (۹۰ ثانیه پس از شروع، مکث ۲۰/۶۰ ثانیه). دانلود عکس: حداکثر ۳ هم‌زمان، ۳۶ نامزد، ۵ مگابایت.
* جدول‌های پس‌زمینهٔ هوشمند (`SmartTasks`، `SmartResearchCaches`، `SmartContentConfigs`، `BlogPlanItems`، `CustomerReminders`) در `PageCachePolicy.IgnoredTypes`
  هستند تا نوشتن در صف، کش صفحه‌های عمومی را خالی نکند؛ فقط تغییر واقعی کالا/دسته/بلاگ کش را باطل می‌کند.
* مسیر `/api/helper/*` (long-poll دستیار محلی) از کاهش بار (load shedding) و ثبت آنلاین‌ها مستثناست و محدودیت جداگانه دارد (۲۴۰ در دقیقه)؛
  هر درخواست حداکثر ۲۵ ثانیه منتظر می‌ماند و نخ (thread) اشغال نمی‌کند.
* راهنمای خریدار صفحهٔ محصول آمار تحویل را ۶ ساعت و راهنماهای بلاگ را ۳۰ دقیقه کش می‌کند و صفحه همچنان OutputCache می‌شود.
