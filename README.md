# Fratak Shop

فروشگاه اینترنتی فارسی (RTL) با **ASP.NET Core 10 Razor Pages**، **EF Core 10 / SQL Server** و معماری سه‌لایه.

## معماری

```
src/
├── Fratak-Shop.Data   → لایه داده: Entity ها، Configuration ها، DbContext، Migration ها، Seeder داده مرجع (استان/شهر)
├── Fratak-Shop.Core   → لایه سرویس: DTO ها، Mapper ها، سرویس‌ها (قوانین کسب‌وکار، اعتبارسنجی، OperationResult)
└── Fratak-Shop.Web    → لایه وب: Razor Pages فروشگاه، سرویس‌های نمایشی، ViewComponent ها، استایل و اسکریپت
tests/
└── Fratak-Shop.Tests  → تست واحد (xUnit) و تست یکپارچه روی SQL Server واقعی
```

| لایه | وابستگی | مسئولیت |
|------|---------|---------|
| Web  | Core, Data | صفحات، احراز هویت (JWT در کوکی HttpOnly)، سبد خرید مهمان، سئو، درگاه پرداخت |
| Core | Data | منطق کسب‌وکار؛ صفحات هرگز مستقیم به DbContext دسترسی ندارند |
| Data | — | مدل داده و دیتابیس |

### لایه وب (`Fratak-Shop.Web`)

| مسیر | توضیح |
|------|-------|
| `Infrastructure/` | `SiteContext` (تنظیمات دیتابیسی هر درخواست)، `Auth/` (JWT + Refresh Token)، میان‌افزارهای امنیتی/URL کانونیکال/ریدایرکت سئو، Rate Limiting، sitemap و robots، سرویس پس‌زمینه انقضای سفارش‌ها |
| `Services/` | سبد خرید (کاربر/مهمان با کوکی + ادغام پس از ورود)، ورود/خروج (JWT)، لیست مقایسه، متادیتای سئو و JSON-LD، کد یک‌بارمصرف و پیامک، درگاه زرین‌پال |
| `ViewComponents/` | هدر سایت (مگامنو دسته‌بندی‌ها با کش، مینی‌سبد، منوی حساب) |
| `Helpers/` | قالب‌بندی قیمت و تاریخ شمسی، برچسب‌های وضعیت، آدرس تصاویر، مجموعه آیکون‌های قالب |
| `Pages/` | صفحات فروشگاه و ناحیه کاربری (`Pages/Profile`) و پرداخت (`Pages/Payment`) |
| `Areas/Admin/` | پنل مدیریت (`/admin`)؛ زیرساخت آن در `Infrastructure/Admin/` (دسترسی‌ها، پایش، خروجی Excel/CSV، موتور جداول) |

## پنل مدیریت (`/admin`)

پنل در Area به نام `Admin` است، کاملاً واکنش‌گرا (منوی کشویی در موبایل، جدول‌ها به شکل کارت) و فقط برای کارمندان؛
برای مشتری و مهمان وجودش افشا نمی‌شود (۴۰۴) و همه‌ی پاسخ‌ها `no-store` و `noindex` هستند.

**مدیران اصلی:** در `Shop:DefaultAdmins` هر تعداد مدیر (کلید ثابت، موبایل، نام، دسترسی کامل یا نقش‌های مشخص) تعریف کنید؛
در هر اجرا بررسی می‌شوند: اگر نباشند با رمز اولیهٔ `Shop:DefaultAdminPassword` (پیش‌فرض `12345678`) ساخته می‌شوند، تغییرات خودشان (شماره، نام، رمز) هرگز برنمی‌گردد و همیشه فعال و با دسترسی می‌مانند و بقیه‌ی کارمندان و نقش‌ها را از خود پنل مدیریت می‌کنند (جزئیات: `docs/DEPLOYMENT.md`). داده‌ی نمایشی: مالک `09120000009`، و `0912000000{2..6}` به ترتیب فروش، سئو، نویسنده، فنی، حسابداری (رمز `123456`).

### نقش‌ها و دسترسی‌ها

* نقش‌ها پویا هستند (`AdminRoles`, `AdminRolePermissions`, `UserAdminRoles`): هر نقش مجموعه‌ای دلخواه از دسترسی‌های ریز
  (مشاهده/مدیریت سفارش، لغو، فاکتور خرید، محصولات، لینک تأمین‌کننده، مشتریان، کیف پول، مالی، خروجی مالی، بازاریابی، وبلاگ نوشتن/انتشار، سئو، محتوا، تنظیمات، پایش، گزارش فعالیت، ...).
  نقش‌های پیش‌فرض (مدیر، فروش، انبار، پشتیبانی، حسابداری، بازاریابی، سئو، نویسنده، سردبیر، فنی) یک‌بار ساخته می‌شوند و قابل ویرایش‌اند.
* هر صفحه و هر عملیات (Handler) با `[AdminPermission]` محافظت می‌شود و منو فقط بخش‌های مجاز را نشان می‌دهد.
* **جلوگیری از افزایش دسترسی:** کسی نمی‌تواند نقشی بسازد یا بدهد که دسترسی‌اش از خودش بیشتر است، نقش خودش را تغییر دهد یا به مالک دست بزند.
  تغییر نقش‌ها فوراً اعمال می‌شود (کش دسترسی باطل می‌شود) و در رویدادهای امنیتی ثبت می‌شود.

### دور نوزدهم – محتوای هوشمند و فروش هوشمند

پنل ← «محتوای هوشمند» (`/admin/smart`): تکمیل یک‌کلیکی کالا (عکس از منابع معتبر، مشخصات با توافق چند منبع، خلاصهٔ نظر خریداران)،
توضیح و بنر دسته، تقویم و نویسندهٔ بلاگ با دروازهٔ کیفیت، خلاصهٔ روزانهٔ فروش و محافظ سود؛ در فروشگاه: راهنمای خریدار در صفحهٔ محصول
(کمترین قیمت ۳۰ روز، مقایسه با ترب، زمان واقعی تحویل، جایگزین‌ها)، اصلاح کیبورد اشتباه در جست‌وجو، پرسش‌نامهٔ انتخاب و نوار ارسال رایگان.
همه داخلی و رایگان، بدون الگوی فریبنده؛ دستیار محلی اختیاری در `tools/Fratak-Helper`. جزئیات: [`docs/SMART-CONTENT.md`](docs/SMART-CONTENT.md).

## اجرا

پیش‌نیاز: .NET SDK 10 و SQL Server. راهنمای کامل انتشار روی سرور (shop.fratak.ir، IIS/Plesk یا Nginx، متغیرهای محیطی، عیب‌یابی ۴۰۳/۵۰۳): [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).

```bash
dotnet run --project src/Fratak-Shop.Web
```

در اولین اجرا Migration ها اعمال می‌شوند و دیکشنری استان/شهر ثبت می‌شود. دو پرچم `Shop` در `appsettings*.json`:

* `SeedDefaultData` (پیش‌فرض `true`): دادهٔ پیش‌فرض سیستم (تنظیمات و نام فروشگاه، همهٔ صفحات، سؤالات متداول، منوها، صفحهٔ اصلی، مترادف‌ها و
  جست‌وجوهای پیشنهادی، قالب اعلان‌ها، نقش‌ها، …) **فقط روی دیتابیس کاملاً تازه** ساخته می‌شود و در اجراهای بعدی هرگز دوباره ساخته نمی‌شود.
* `SeedDemoData` (توسعه `true`، Production `false`): دادهٔ نمایشی (دسته‌بندی، برند، محصول، بنر، مقاله، کد تخفیف و یک سفارش نمونه) و کاربران نمونه.

مدیران اصلی (`Shop:DefaultAdmins`، پیش‌فرض **09913181090 – محمدامین ناظری** با کلید `owner` و **09134426156 – محمد حسن پیراینده** با کلید `partner`، رمز اولیهٔ `12345678`) با همهٔ دسترسی‌ها ساخته می‌شوند؛
بعد از اولین ورود به «پروفایل ← رمز عبور» فرستاده می‌شود تا رمز را عوض کند. رمز موجود هرگز بازنویسی نمی‌شود؛ حذف، مسدودسازی و برداشتن مالکیت مدیران اصلی در پنل ممنوع است
و اگر به هر دلیل حذف یا مسدود شده باشند، در اجرای بعدی برگردانده می‌شوند.

دادهٔ نمایشی – کاربر نمونه ۲٬۰۰۰٬۰۰۰ تومان موجودی کیف پول و ۱٬۵۰۰ امتیاز باشگاه دارد:

| نقش | موبایل | رمز عبور |
|-----|--------|----------|
| مشتری نمونه | `09120000000` | `123456` |

پاک‌سازی فایل‌های ساختنی (bin/obj/node_modules/.vs): `tools/clean.sh` یا `tools/clean.ps1` (گزارش حجم بدون پاک کردن: `--report` / `-Report`).

## احراز هویت

* مرورگر: Access Token (JWT، ۱۰ دقیقه) و Refresh Token (چرخشی، تشخیص استفاده مجدد) در کوکی‌های HttpOnly؛ تمدید خودکار و بی‌صدا.
* API / اپ موبایل: `POST /api/auth/token` ، `POST /api/auth/refresh` ، `POST /api/auth/revoke` ، `GET /api/auth/me` با هدر `Authorization: Bearer`.
* تغییر رمز یا «خروج از همه دستگاه‌ها» همه توکن‌ها را فوراً باطل می‌کند.
* کارکنان می‌توانند (یا با تنظیم «اجباری» باید) برنامهٔ احراز هویت (TOTP) را از `/admin/account` فعال کنند؛ در این حالت هر ورود (رمز، کد پیامکی، `/login/2fa`)
  کد برنامه یا یک کد بازیابی می‌خواهد و `POST /api/auth/token` بدون فیلد `TotpCode` پاسخ ۴۰۱ با `"totpRequired": true` می‌دهد.

## پرداخت (زرین‌پال)

پرداخت سفارش و شارژ کیف پول به درگاه زرین‌پال (API v4) هدایت می‌شود. حالت آزمایشی با `ZarinPalSandbox = true` در `StoreSettings` فعال است
(مرچنت آزمایشی پیش‌فرض ثبت شده). برای Production مرچنت واقعی را ثبت و Sandbox را خاموش کنید. تایید پرداخت فقط سمت سرور و یک‌بار انجام می‌شود؛
پرداخت دیرهنگام یا تکراری به کیف پول برگشت داده می‌شود.

## نقاط توسعه

* **PWA:** پیشنهاد نصب پس از چند بازدید (`PwaInstallPromptAfterPages`) و تعویق با «بعداً» (`PwaInstallPromptSnoozeDays`)؛ در آیفون راهنمای «Add to Home Screen». `/sw.js` فقط فایل‌های ثابت (css/js/فونت) را کش می‌کند؛ صفحات HTML و درخواست‌های POST هرگز کش نمی‌شوند و در حالت آفلاین `/offline.html` نمایش داده می‌شود. با خاموش کردن `IsPwaEnabled` سرویس‌ورکر نصب‌شده خودکار حذف می‌شود.
* **کارهای زمان‌بندی‌شده:** هر ۵ دقیقه لغو سفارش‌های پرداخت‌نشده، پاک‌سازی توکن‌ها و پیگیری سبدهای رهاشده؛ هر ساعت هدیه تولد و انقضای امتیازها (`OrderMaintenanceService`).
* **کیف پول دوبخشی:** موجودی قابل برداشت (پول خود مشتری) و اعتبار هدیه (باشگاه/جشنواره، فقط برای خرید). در خرید ابتدا اعتبار هدیه مصرف می‌شود و در لغو/مرجوعی هر سهم به همان نوع برمی‌گردد.
* **فاکتور:** برگه A4 ثابت (مستقل از اندازه صفحه)، چاپ و PDF دقیقاً همان برگه، شماره سریال پس از پرداخت (`InvoiceNumberPrefix`)، چاپ مستقیم از صفحه سفارش.
* **گزارش‌های مدیریتی (فقط داده):** `IReportService` (تخفیف‌ها، امتیاز و اعتبار هدیه، سود بر اساس قیمت خرید ثبت‌شده در هر قلم سفارش) و `IAbandonedCartService.GetStatsAsync`. در Development خروجی JSON از `/_dev/reports` (فقط از خود سرور) در دسترس است.
* **تصاویر دیدگاه:** در `/uploads/comments/` با نام تصادفی ذخیره می‌شوند؛ محتوای واقعی فایل (JPG/PNG/WebP) بررسی و اطلاعات اضافه (EXIF/GPS، XMP، توضیحات، داده انتهای فایل) حذف می‌شود (`ImageSanitizer`، بدون System.Drawing).
* **پیامک:** `ISmsSender` — پیاده‌سازی فعلی پیامک را در لاگ می‌نویسد (و در Development کد تایید روی صفحه نمایش داده می‌شود)؛ برای Production یک ارائه‌دهنده (کاوه‌نگار، SMS.ir، ...) ثبت کنید.
* **کش خروجی صفحات:** صفحات عمومی (اصلی، لیست‌ها، محصول، وبلاگ، صفحات محتوایی) برای بازدیدکننده‌ی **بدون کوکی** کش می‌شوند (هدر `X-Page-Cache: HIT`).
  هر تغییر داده از طریق `DbContext` (محصول، قیمت، موجودی، دیدگاه، تنظیمات، منو، ...) کش‌های مربوط را فوراً پاک می‌کند (`DataChangeNotifier` → `CacheInvalidation`)
  و نسخه کاتالوگ را بالا می‌برد؛ کاربر واردشده، سبد دارای کالا یا درخواست POST هرگز صفحه کش‌شده نمی‌گیرد. توکن ضدجعل فرم‌ها در صفحات کش‌شده با `/api/antiforgery` گرفته می‌شود.
* **تصاویر بهینه:** `/media/{w}/{path}` تصویر را با SkiaSharp به WebP با عرض استاندارد (۱۶۰ تا ۱۲۸۰) تبدیل و روی دیسک کش می‌کند؛ صفحات با `srcset` و `loading="lazy"` از آن استفاده می‌کنند.
* **کپچا:** پس از چند تلاش ناموفق (`CaptchaAfterFailures`) در ورود، ارسال کد، ثبت‌نام، تماس، کارت هدیه و پیگیری سفارش نمایش داده می‌شود (SVG سمت سرور، بدون سرویس خارجی).
* **پوش مرورگر:** Web Push استاندارد (VAPID + رمزنگاری aes128gcm بدون کتابخانه خارجی)؛ فقط به سرویس‌های پوش شناخته‌شده ارسال می‌شود.
* **حالت تاریک:** `theme.js` قبل از رندر صفحه کلاس `dark` را اعمال می‌کند (بدون پرش رنگ) و انتخاب کاربر در `localStorage` می‌ماند؛ پیش‌فرض از `StoreSettings.DefaultTheme`.
* **سئو:** عنوان/توضیح/canonical/OG/robots/JSON-LD از رکورد سئوی هر موجودیت یا صفحه (`PageSeos`)؛ JSON-LD محصول (پیشنهاد، امتیاز، دیدگاه، ویدیو، سیاست مرجوعی)، مقاله،
  مسیر (Breadcrumb)، سوالات متداول، سازمان و جستجوی سایت. صفحات شخصی/تراکنشی (`PrivatePaths`) همیشه `noindex` هستند و همان فهرست در robots.txt قرار می‌گیرد.
* **تصاویر:** نام فایل‌های آپلودی از مسیر `/uploads/{products|categories|blogs|banners|brands}/` خوانده می‌شود (`Helpers/ImageHelper`).

## Migration

```bash
dotnet ef migrations add <Name> --project src/Fratak-Shop.Data --startup-project src/Fratak-Shop.Data
```

(`FratakShopDbContextFactory` رشته اتصال طراحی را از متغیر محیطی `FRATAK_SHOP_CONNECTION` می‌خواند.)

## تست‌ها

```bash
# فقط تست‌های واحد (بدون دیتابیس)
dotnet test --filter "Category!=Integration"

# همه تست‌ها؛ تست‌های یکپارچه یک دیتابیس موقت می‌سازند و در پایان حذف می‌کنند
export FRATAK_TEST_SQL="Server=localhost,1433;User Id=sa;Password=...;TrustServerCertificate=True"
dotnet test
```

* **واحد:** کد کارت هدیه، نرمال‌سازی متن و جستجوی فازی، اسلاگ، XSS، رمزنگاری Web Push، اعتبارسنجی کارت/شبا، هش رمز، قوانین سفارش و قیمت،
  تشخیص دستگاه، لینک ویدیو، پاک‌شدن کش، سیاست کش صفحات، `srcset`، قالب تاریخ، کپچا و سئو.
* **یکپارچه (SQL Server واقعی، همان Migration ها و Seeder ها):** کیف پول دوبخشی و برداشت هم‌زمان، خرید و ثبت کارت هدیه (یک‌بار مصرف حتی هم‌زمان، قفل حدس کد)،
  خرید بعدی، به‌روزشدن فوری تنظیمات و مترادف‌ها پس از تغییر، نقش‌ها و جلوگیری از افزایش دسترسی، الزام فاکتور خرید پیش از آماده‌سازی.
* **پنل مدیریت (واحد):** محافظت همه‌ی صفحات با دسترسی معتبر، منو، پوشش کامل فیلدهای تنظیمات، صحت جداول موتور عمومی، بازه‌های گزارش و تاریخ شمسی، خروجی CSV/XLSX (ضد Formula Injection).
* **مرحلهٔ هفتم:** برای هر فاز یک فایل واحد و یک فایل یکپارچه، از جمله `AdminUxTests`، `AdminTablesTests`، `OrdersRound7Tests`، `SupplierSyncTests`، `PostTrackingTests`/`PostCaptchaTests`،
  `InsightsTests`، `SeoEngineTests`/`SeoToolsTests`، `OpsTests` و `TeamTests` (بردارهای رسمی RFC 6238، کوکی تأیید دوباره، `[RequireReauth]` روی کارهای حساس، پوشاندن اطلاعات)
  و در `Integration/` روندهای کامل روی SQL Server (مثلاً تأیید دونفره از درخواست تا اجرای واقعی، TOTP با قفل و بازنشانی، پشتیبان‌گیری واقعی و فایروال).

## CI

* `Build` — بیلد کامل Solution و تست‌های واحد.
* `Verify` — بیلد هر پروژه با گزارش کامل خطاها، و اجرای برنامه روی SQL Server واقعی همراه با **تست دود سرتاسری**
  (`.github/scripts/smoke-test.sh`): همه صفحات عمومی، ورود، سبد خرید، ثبت سفارش پرداخت در محل، پرداخت اینترنتی با درگاه آزمایشی،
  ثبت دیدگاه، علاقه‌مندی، فرم تماس و ثبت‌نام، کش صفحات و سئو، و **پنل مدیریت** (عدم دسترسی مشتری، باز شدن همه‌ی صفحات/زبانه‌ها/جداول/جزئیات و خروجی‌ها برای مالک، محدودیت نقش نویسنده)؛ سپس همه تست‌ها (واحد + یکپارچه) روی SQL Server. خطاها به‌صورت کامنت روی commit ثبت می‌شوند.
* راهنمای تست دستی هر فرایند: [`docs/QA-CHECKLIST.md`](docs/QA-CHECKLIST.md).
